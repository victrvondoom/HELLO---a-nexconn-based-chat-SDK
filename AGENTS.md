# AGENTS.md: working notes for coding agents

This file is the project memory. Keep it true. A feature is complete only when its user journey works and its
evidence is recorded in `docs/TEST_EVIDENCE.md`.

## Project purpose

HELLO is an event coordination app built on the Nexconn chat SDK. It covers attendees, staff, incidents, approvals,
venue maps, communities, calls, games and a workflow canvas. HELLO FIELD ATLAS adds mission-based progression to it.

## Architecture

- Next.js App Router (`src/app`). Pages are server components that call `loadEventViewer` (`src/lib/viewer.ts`).
  Interactive islands are `'use client'` components.
- Services (`src/services/*`) hold the business rules. Routes (`src/app/api/**`) parse input, then call a service.
- Pure domain rules (`src/domain/**`) have no storage and no clock. They are unit tested.
- Persistence is the `HelloStore` contract (`src/store/store.ts`). Two implementations: `PostgresHelloStore`
  (`src/store/postgres.ts`, chosen by `DATABASE_URL`) and `MemoryHelloStore` (`src/store/memory.ts`, optionally saved
  to disk by `src/lib/persistence.ts`, `HELLO_DATA_DIR`). Any store change must pass `npm run test:postgres` too.
- Live updates: every store write publishes a content-free nudge (`src/lib/live/store.ts` `describeWrite` is the
  policy; personal and staff topics go only to the people concerned). `GET /api/events/[eventId]/stream` (SSE) delivers
  them; `useLive` and `LiveRefresh` refetch through the normal API. Postgres fans them out across instances.
- Chat gateway (`src/services/chat-gateway.ts`, `src/integrations/chat/`): Nexconn plugs in here. See
  docs/nexconn-integration.md.
- Shared per-person write limits for app routes and MCP tools: `src/lib/action-limits.ts`.
  Product records use typed document collections (`docGet/docPut/docPutIfAbsent/docMutate/docList`).
- Authorisation: `requireCapability(ctx, eventId, userId, capability)` (`src/services/context.ts`) against the table
  in `src/domain/permissions.ts`. Hiding a control in React is never the security boundary.

## Field Atlas (`src/domain/field`, `src/services/field-atlas.ts`, `src/services/quest-director.ts`)

Pages: `/events/[eventId]/atlas` (attendee) and `/events/[eventId]/atlas/manage` (organiser and operations).
API: `/api/events/[eventId]/atlas/**`. Components: `src/components/atlas/*`. Seed: `src/store/field-seed.ts`.

### Progression invariants

1. XP is the sum of `fieldLedger` entries for a person in an event. Nothing else stores XP.
2. A ledger entry id is derived from its source (`${userId}:mission:${missionId}`, `${userId}:season:${seasonId}`).
   `docPutIfAbsent` makes a repeated award a no-op.
3. An attempt (`${missionId}:${userId}`) moves to `APPROVED` once, through a conditional `docMutate`. Only the call that
   wins that transition awards anything. Concurrent submissions were tested to award exactly once.
4. Levels are derived: the highest active level whose minimum XP is reached and whose required achievements are held.
   Level definitions are per event (`fieldLevels`), defaulting to `DEFAULT_LEVELS`.
5. Adjustments are `ADJUSTMENT` ledger entries with a reason of at least 10 characters. Existing entries are never
   edited or deleted, and each adjustment is audited.
6. Badges (`fieldBadges`) are never revoked. Season expiry does not remove them.

### Verification rules

A mission declares exactly one method:

- `WORKFLOW_RUN`: approved only when a succeeded run of the named workflow by this person started after the attempt.
- `CHECK_IN`: approved only when the code matches the station's current code and it has not expired (4 hours).
  Codes are generated by `issueStation`, shown once, and stored only as a salted-by-id SHA-256 hash.
  Stations seeded for the demo have no code (`codeExpiresAt = 0`), so no demo check-in can succeed without staff.
- `MANUAL_REVIEW`: never approved automatically. Evidence goes to `PENDING_REVIEW`. An organiser or operations staff
  member approves or sends it back. Up to three submissions per mission.

The policy is `decideVerification` in `src/domain/field/rules.ts`. AI never reaches it.

### Seasons and badges

- Seasons use calendar months in the event's time zone (`monthWindow(year, month, timeZone)`).
- A monthly badge is earned when every required mission is approved inside the season window. The bonus XP is awarded
  with it, once.
- Permanent achievements (`FIRST_MISSION`, `FIVE_MISSIONS`, `WAYFINDER`) are evaluated after each approval.

### Quest Director

- `fieldGuide`: answers about one mission, citing `kind:id.field` for each answer. Deterministic, no model.
- `recommendFor`: ranks missions by fit, and routes with `findRoute` when a starting place is chosen. Locations are
  never tracked.
- `draftMonthlyChallenge`: drafts a month from real rooms, stations and workflows. Gaps are listed as unavailable.
  Drafts pass `MissionSchema`. Only low-risk workflow missions (XP ≤ 50, no level gate) publish themselves.
- Quest Director does not call a language model. Its output is deterministic and says so. It cannot award XP,
  verify evidence, or change a reward.

### Live layer: Field Conditions and Season Pulse (`src/domain/field/live.ts`, `src/services/field-live.ts`)

- `atlasHome` builds the atlas payload for both the page and `GET /api/events/[eventId]/atlas`. Add fields there only.
- Field Conditions: per venue space with a room, from open incidents (`isOpen`), room occupancy/capacity and the
  session running now. Levels CLEAR < BUSY < CAUTION < AVOID. Attendees get a category and a count, never incident
  text or ids. Read on every poll; nothing is stored.
- Season Pulse: aggregate counts per mission (verified in the last hour, underway, completed) and per season. Every
  count below `PULSE_MIN_COUNT` (3) is null and shown as "fewer than 3", so no count can single out a person.
- Quest Director applies `conditionPenalty` and `pulsePenalty` and cites `condition:<spaceId>` / `pulse:<missionId>`.
  The field guide answers "Is now a good time to go?" from the same conditions. Neither changes availability or awards.

### Integrity flags

- One OPEN flag per (person, mission, kind). The id is a hash of the source and the dismissed count (`flag` in
  `field-atlas.ts`), so retries do not flood the queue and the id does not carry the user id.
- Only PUBLISHED seasons award a bonus, and every season that requires the approved mission is checked.
- An XP adjustment can never take a person below 0.

### Privacy

- No GPS. Route origin is a place the person picks.
- Evidence text is visible to organisers and to the person who wrote it. The management snapshot never shows it to
  attendees.
- Export includes the person's own Field Atlas records. Erasure deletes their attempts, ledger entries and badges, and
  unlinks their flags. Other people's records are not changed.

## Commands

- `npm run typecheck`, `npm run lint`, `npm test` (vitest), `npm run build`, `npm run check`
- Browser journeys: start the demo server (`HELLO_DEMO_MODE=true npx next start -p 3000`), then
  `node tests/e2e/field-atlas-flow.mjs` and `node tests/e2e/field-live-flow.mjs`. A demo reset clears every rate
  limiter (the registry is on `globalThis`), so runs can follow each other. Run suites one at a time: each resets the demo.
  Stop the server with `pkill -f next-server` (the process name is not `next start`).
- `npm run test:routes` crawls every page as every demo role.
- `npm run test:postgres` with `HELLO_TEST_DATABASE_URL` runs the integration suite on Postgres (one schema per test).
- `npm run test:e2e` runs every browser journey. `tests/e2e/chat-bridge-flow.mjs` needs `HELLO_CHAT_SECRET` and
  `HELLO_CHAT_OUTBOUND_URL=http://localhost:4100/hello` on the server; `live-flow.mjs` takes `BASE_URL_B` for a second
  instance. CI (`.github/workflows/ci.yml`) runs all of it.

## Environment variables

See `.env.example`: `DATABASE_URL`, `HELLO_DB_SCHEMA`, `HELLO_CHAT_SECRET`, `HELLO_CHAT_OUTBOUND_URL` were added. `HELLO_DEMO_MODE` seeds the demo event; `HELLO_DATA_DIR` enables disk
persistence.

## Integration limitations (see docs/INTEGRATION_STATUS.md)

- Nexconn: the chat gateway is built; the Nexconn-side bridge is not written (needs credentials).
- Rate limits are per instance, also on Postgres.
- No AI model provider is configured. Quest Director is deterministic.
